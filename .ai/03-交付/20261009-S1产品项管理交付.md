## 2. D4 决策落地：产品编码由系统生成

这是本阶段唯一与实测企业版 UI 有实质偏离的地方。

### 2.1 编码生成

```
po_ + 12 位小写字母数字   例：po_xbp6sphlemg0
```

- 随机而非递增，避免从编码推测业务量级
- 唯一索引 + 生成重试至多 5 次兜底
- 格式校验函数拒绝任何非 `po_` 前缀的字符（防御其他路径注入）
- 单测含 1000 次唯一性验证

### 2.2 向导字段调整

| 企业版 | 本项目 |
| --- | --- |
| `*产品项编码`（手填 + 格式校验） | **移除手填**，保存后系统生成，只读展示 + 锁图标 |
| — | `别名（可选）`：可改，界面显示用，为空回落编码 |
| `*产品项名称` | 保留 |

### 2.3 不可修改的三重保障

1. 请求结构 `ProductOfferingUpdateRequest` **不含 `Code` 字段**
2. Service 更新时 `updated.Code = existing.Code` 显式回填
3. Repository `Update` 用 `Select(...)` 白名单限定可更新列

**实测验证**：

```
PUT /api/v1/product-offerings/{id}
body: { "name": "NEGLab 分析软件 v2", "code": "po_HACKED_BY_CLIENT", ... }
→ name 已更新，code 仍为 po_xbp6sphlemg0（篡改被忽略）
```

## 7. 实施中发现的问题

### 7.1 错误码状态映射是硬编码白名单

`pkg/i18n/errors.go` 的 `getHTTPStatusByCode` 是 switch 白名单，新前缀未注册会落到 `default` → **返回 500**。最初所有业务校验错误都返回 500，语义完全错误。

已登记 50xxx 前缀并在 `case` 中补充具体码。**后续阶段新增错误码必须同步两处。**

### 7.2 900xxx 不是兜底错误码

`900001`=参数无效(400)、`900002`=资源不存在(404)、`900003`=资源冲突(409)、`900004`=服务器内部错误(500)。初版误用 `900002` 表示「DB 查询失败」，已新增 `900005`「数据库操作失败」→ 500。

### 7.3 `models.JSON` 不能从 map 直接转换

它是 `json.RawMessage` 类型，需 `json.Marshal`。编译期才发现。

### 7.4 `gofmt -w` 目录会误改存量文件

`gofmt -w internal/api/` 重排了 4 个与本次无关的存量文件（本身未格式化）。已 `git checkout` 回退。**应只对单个文件执行。**

### 7.5 Vite 依赖预构建被安全删除守卫拦截

`SAFE_DELETE_BULK_CONFIRM_REQUIRED`（139 文件超阈值）导致 dev server 崩溃。手动 `mv` 出 `node_modules/.vite/deps_temp_*` 后恢复。
