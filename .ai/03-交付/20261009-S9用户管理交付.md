## 2. 企业版实测契约

### 2.1 用户接口

```
GET    /api/v1/users?page&page_size&search&status
POST   /api/v1/users
GET    /api/v1/users/:id
PUT    /api/v1/users/:id
DELETE /api/v1/users/:id
POST   /api/v1/users/:id/reset-password
```

用户响应字段（实测）：`id`/`username`/`email`/`full_name`/`phone`/`status`/`last_login_at`/`created_at`

**注意：企业版用户响应中没有 role 字段** —— 权限靠 `user_roles` 关联表。

### 2.2 `role_assignments` 结构（实测逐步探明）

```
role_assignments: [{ "role": "super_admin" }]     ← 对象数组，用角色名而非ID
```

验证过程：
1. 传字符串数组 → `cannot unmarshal string into UserRoleAssignmentInput`
2. 传 `[]` → 触发 `min` 校验
3. 传 `[{role_id:"x"}]` → `RoleAssignments[0].Role failed on 'required'` → **字段名是 `role`**
4. 传 `[{role:"super_admin"}]` → 创建成功

## 3. 核心设计

### 3.1 角色必须至少一个

企业版 `RoleAssignments` 有 `min=1` 校验。本项目采纳同一口径：

**没有角色的用户登录后什么都看不到** —— 这看起来像"控制台坏了"，而不是"配置漏了"。在创建时就拒绝比创建后困惑更好。

### 3.2 兼容 v1 的 role 字段

`UserCreateRequest.Role`（`admin`/`operator`/`viewer`）保留，映射到等价角色：

```go
admin    → super_admin
operator → operator
viewer   → viewer
```

旧调用方无需了解 `role_assignments` 即可继续工作。

### 3.3 最后一个超级管理员不可停用/删除

否则系统无人可管，且**无法再通过界面找回**。实测两条路径都被 `600017` 拦截。

### 3.4 重置密码同时解除锁定

管理员已确认身份，锁定状态不应继续阻挡。

## 5. 未做：v2 登录（原 S5-5）

原方案是新增 `POST /api/v2/login`，返回 `permissions` 数组、`expires_in=604800`、JWT 不含 `role` claim，v1 保持不变。

**实测企业版 `/api/v2/login` 返回 404**，其 v1 登录已直接返回 `permissions`（56 条）+ `expires_in=604800`。

**企业版实测登录响应**：
```
data: { token, expires_in: 604800, user_info: { username }, permissions: [56 条] }
```

本项目未做 v2 的原因：
1. 权限校验已在 S7 挂在服务端接口上，前端菜单已由 S6 驱动
2. 前端不需要 `permissions` 数组也能正确渲染菜单 —— 后端 `/menus` 已按角色过滤
3. 强行对齐企业版的 604800s 会缩短现有会话，属于行为变更

**建议**：如需对齐，先确认会话时长是否为有意变更，再单独立项。

## 7. 实施中的问题

### 7.1 Gin 路由参数名冲突导致启动 panic

```
panic: ':id' in new path '/api/v1/users/:id' conflicts with existing
       wildcard ':userId' in existing prefix '/api/v1/users/:userId'
```

S6 注册的 `/users/:userId/roles` 与 S9 的 `/users/:id` 在 Gin 看来是**两个不同的路由**（参数名不同）。已统一为 `:id`。

**这条只在启动时暴露，编译和测试都发现不了。**

### 7.2 重复注册同一路由

统一参数名后，`GET /users/:id/roles` 被注册两次（S6 的 rbacHandler + S9 的专用 handler）。Gin 不报错但后者失效。已删除 S6 版本，保留专用 handler。

### 7.3 GORM Scan 无法映射嵌套 struct

```go
type row struct {
    UserID string
    Item   models.UserRoleItem   // ← Scan 无法映射
}
```

报错 `invalid field found for struct row's field Item`。改为平铺字段 + `RoleID` 别名。

**教训：GORM 的 `Scan` 只支持平铺字段，嵌套 struct 需显式实现 Valuer/Scanner。**

### 7.4 错误码落错 YAML 块

`200011`（用户名重复）被插入到 `rbac:` 块下，会被解析成 `rbac.200011` 而查不到。已移到 `customer:` 块。

**教训：YAML 错误码是按模块分块的，插错块等于没插。**

### 7.5 重复定义模型

`user_management.go` 中重复定义了 `UserCreateRequest`/`UserUpdateRequest`/`UserListRequest`/`UserListItem`/`UserListResponse`，与 `user.go` 冲突。已改为扩展原有类型。
