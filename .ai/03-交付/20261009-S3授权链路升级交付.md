## 2. 对 S1 的修正（本阶段最重要产出）

### 2.1 问题

S1 我给产品项加了 `deployment_mode`（online/offline/hybrid），**当时是推断的，没实测企业版授权码接口**。S3 实测 1026 条数据后发现：

| 来源 | 口径 |
| --- | --- |
| 企业版实测（1026 条授权码） | `deployment_type`: `standalone`/`cloud`（单机版/云端版）<br>`validity_mode`: `fixed`/`activation_based`（固定期限/从激活起算） |
| 企业版**产品项**接口 | **无任何部署字段** |
| 官方文档 | 「部署模式：在线（云端）/离线（单机）/混合」 |
| 社区版历史 `5ac72db` | **主动删除** `deployment_type`，迁移 011 注明「社区版不区分部署类型和加密类型」 |

**我的 S1 字段在企业版产品项上并不存在**，且与社区版已删除的历史字段语义撞车。

### 2.2 决策

已向小黄确认，**选择按文档口径**：

| 层 | 字段 |
| --- | --- |
| 产品项 | `deployment_mode`（online/offline/hybrid）—— 文档口径，声明该产品的默认交付方式 |
| 授权码 | **额外**采用企业版真实字段 `deployment_type`（standalone/cloud）+ `validity_mode`（fixed/activation_based）+ `duration_days` |

两套并存：产品项声明「这个产品怎么交付」，授权码声明「这一张码具体是什么形态」。

### 2.3 连带修复

`deployment_type` 列在社区版已被迁移 011 删除，而 `removeLegacyAuthorizationCodeTypeFields()` 在 AutoMigrate **之后**会再次删除该列 —— 导致查询报 `Unknown column 'ac.deployment_type'`。

已将该清理函数收窄为仅清理 `encryption_type` 与两个历史索引。

## 3. 默认策略继承规则

| 字段 | 请求未指定时 | 最终兜底 |
| --- | --- | --- |
| 有效期 | 产品项 `duration_days` | 365 天 |
| 激活上限 | 产品项 `max_activations` | 1 |
| 功能配置 | 产品项 `feature_config` | 空 |
| 使用限制 | 产品项 `usage_limits` | 空 |
| 自定义参数 | 产品项 `custom_parameters` | 空 |
| 部署类型 | 产品项 `deployment_mode=offline` → `standalone`，否则 `cloud` | `cloud` |

**显式传入的字段始终优先**，继承只填补空缺。

### 校验规则

| 规则 | 错误码 | 理由 |
| --- | --- | --- |
| 产品项已停用 | `300013` | 停用产品不应再发码 |
| 有效期 > 产品体验天数 | `300014` | 授权码长于体验期是肉眼难察的 bug |
| 批量数量 > 100 | `300015` | 防止一次误操作生成海量授权码 |

**实测**：NEGLab 产品项为 15 天体验型，传 365 天 → `300014` 拒绝。

## 7. 实施中的问题

### 7.1 `gofmt -w internal/` 再次误改 7 个存量文件

S1 踩过的坑又踩一次。已 `git checkout` 回退。

**教训固化**：只对本次实际修改的文件跑 gofmt，绝不对目录执行。

### 7.2 `binding:"max=100"` 击穿业务错误码

批量创建的 `Count` 加了 `binding:"max=100"`，结果超上限时框架先拦成 `900001`（字段校验失败），service 层的 `300015`「单次批量创建数量不能超过 100」永远走不到。

框架消息只说「字段校验失败」，不说规则。已移除 binding 上限，校验下移 service。

### 7.3 清理函数与新字段冲突

`removeLegacyAuthorizationCodeTypeFields()` 在 AutoMigrate 之后运行，会把刚建好的 `deployment_type` 列删掉。这类「先建后删」的顺序陷阱在迁移脚本里很隐蔽。
