## 3. 核心设计

### 3.1 成功/失败判定不能只看 HTTP 状态码

本项目业务错误以 **HTTP 200 + 响应体 `code`** 表达（见 `200005` 约定）。仅看状态码会把所有失败记成成功。

因此实现了 `AuditResponseWriter` 包装 `gin.ResponseWriter`，捕获响应体后解析 `code` 字段判定：

```
000000 → success
其他   → failure
```

### 3.2 只记录写操作

`POST`/`PUT`/`PATCH`/`DELETE` 记录，`GET`/`HEAD`/`OPTIONS` 跳过。否则日志量会淹没真正需要追溯的变更。

**实测**：触发一次 GET 后 `total` 保持不变。

### 3.3 审计是旁路操作

写入失败仅记入请求上下文，**不影响业务响应**。审计不能成为业务可用性的单点。

### 3.4 请求/响应体按原文保存

存字符串而非解析为对象：审计需要保留实际发送的内容，解析会丢弃尚未被本代码认识的字段。

单条限 4096 字节，超出截断并标注。

## 7. 实施中的问题

### 7.1 类型断言静默失败导致 detail 全空

`c.Set(key, *bytes.Buffer)` 存入的是指针，取出时却按 `string` 断言：

```go
if s, ok := captured.(string); ok { respBody = s }  // 永远 false
```

`ok` 为 false 时静默跳过，detail 里 `req_body`/`resp_body` 全空 —— 但 HTTP 层一切正常，只能靠读数据库发现。

已改为 `switch` 同时处理 `*bytes.Buffer` 与 `string`。

**教训：gin.Context 取值必须确認存入时的实际类型。**

### 7.2 版本号前缀未剥离导致资源类型错误

单测 `TestResolveAuditResource` 暴露：`/v1/customers` 的 resourceType 返回 `v1` 而不是 `customers`。

原代码只剥 `api` 前缀，没处理 `/v1/xxx` 形式（企业版路径就是这种）。

已补 `isVersionSegment`。

**这条是单测的直接价值 —— 手测大概率会漏。**

### 7.3 日文 i18n 再次出现替换字符

同 S4，批量写多语言文案时 ja 串混入 `U+FFFD`。已用 JSON 读出改写方式修复。

## 8. 遗留

- **激活/心跳接口不审计**：走 public 组，客户端高频调用会撑爆日志表。企业版记录了，但建议本项目保持不记录
- **操作人下拉未做**：后端支持 `user_id` 筛选，前端未加操作人下拉（当前列表已显示操作人列）
- **日志清理策略未定**：`audit_logs` 会持续增长，生产环境需定期归档或清理策略（S9 之后考虑）
