# 社区版与企业版功能差异清单

> 目标：为「获取企业版完整功能」提供可执行的差异基线，明确补齐范围与依赖顺序。
>
> 本文清单以**企业版在线演示环境的实测接口**为准，不依赖二手描述。

---

## 1. 结论先行

| 项 | 结论 |
| --- | --- |
| 企业版模块总数 | **16 个**权限资源（实测 admin 权限清单） |
| 社区版已具备 | **4 个**：客户、授权码、许可证、仪表盘 |
| 企业版独有 | **12 个**：产品项、功能模板、设备台账、审计日志、系统配置、用户管理、角色权限、菜单管理、API Key、发票、套餐、企业线索 |
| 架构级差异 | 企业版基于 **Casbin RBAC**（细粒度 `资源:操作` 权限），社区版仅 `role` 字符串单向判断 |
| 数据模型差异 | 企业版授权链路为 `产品项 → 授权码 → 许可证` 三层，社区版为 `客户 → 授权码 → 许可证` 两层，**缺少产品项这一归口层** |
| 客户自助端 | 企业版独立前台（注册/下单/支付/自助取码/解绑/开票），社区版完全没有 |
| 建议策略 | **不建议盲目补齐 12 个模块**。产品项 + 功能模板是授权体系的地基，必须先做；客户自助端是独立业务线，应独立立项 |

## 4. 关键差异详述

### 4.1 客户字段差异

社区版 `customers` 表缺两个字段，但设计文档已定义 —— 说明是实现遗漏而非产品裁剪：

| 字段 | 文档定义 | 代码实现 | 状态 |
| --- | --- | --- | --- |
| `company_size` | small / medium / large / enterprise | 模型有字段，DB 列缺失 | ⚠️ |
| `customer_level` | basic / active / vip / strategic | 默认 `basic` | ⚠️ 枚举值与文档不一致 |

`customer_level` 文档枚举（normal/vip/enterprise/strategic）与模型默认 `basic` 冲突，需对齐。

### 4.2 授权链路缺产品项层

**社区版现状**：

```
customers ──< authorization_codes ──< licenses
                    │
                    └──< authorization_changes
```

授权策略（`feature_config` / `usage_limits` / `custom_parameters`）直接挂在授权码上，`software_id` 仅为游离字符串。

**企业版现状**：

```
product_offerings ──< authorization_codes ──< licenses
        │                   │
  feature_templates    authorization_changes
```

产品项实测字段：

```json
{
  "id": "deff875f-...", "name": "产品A", "code": "PROD-A",
  "status": "active", "is_trial_product": true, "trial_days": 15,
  "feature_config": {}, "usage_limits": {}, "custom_parameters": {},
  "user_count": 5, "auth_code_count": 15
}
```

**注意 `is_trial_product` + `trial_days`** —— 社区版授权码没有试用/正式的概念区分，只能靠 `start_date`/`end_date` 硬编码。

功能模板实测字段：

```json
{
  "id": "9d2cf13c-...", "name": "专业版模板",
  "identifier": "pro_template", "category": "general",
  "feature_config": [], "sort_order": 0,
  "status": "active", "is_system": false
}
```

**影响**：不补产品项，`is_trial_product`、`user_count`、产品级签名密钥、模板复用都无法落地。这是**第一优先级**。

### 4.3 客户端公开接口差异

| 接口 | 企业版 | 社区版 |
| --- | --- | --- |
| `POST /api/v1/activate` | ✅ | ✅ |
| `POST /api/v1/heartbeat` | ✅ | ✅ |
| `POST /api/v1/licenses/by-fingerprint` | ✅ 200 | ❌ 404 |
| `GET /api/public/config` | ✅ 200 | ❌ 404 |
| `POST /api/cu/packages` | ✅ 200（公开） | ❌ 404 |
| `POST /api/leads` | ✅ 200（公开） | ❌ 404 |
| `POST /api/v1/activate`（错误码格式） | `message: "success"` | `message: "成功"` |

⚠️ **i18n 不一致**：企业版返回英文 `"success"`，社区版返回中文 `"成功"`。若未来合并或对接同一客户端，需统一。

### 4.4 认证与授权架构差异

**登录响应结构对比**：

| 字段 | 社区版 | 企业版 |
| --- | --- | --- |
| `expires_in` | `3600`（1 小时） | `604800`（7 天） |
| `user_info.role` | ✅ `admin` | ❌ 无 role |
| `user_info.permissions` | ❌ 不存在 | ✅ **56 条** `资源:操作` |
| JWT `iss` | `license-manager` | `license-manager` |
| JWT `role` claim | ✅ | ❌ |

企业版实测角色列表含 `super_admin`、`product_admin` 等，权限资源 16 类：

```
api_key(4) audit_log(1) authorization_code(4) customer(4) dashboard(1)
device_ledger(4) feature_template(4) invoice(4) lead(4) license(4)
menu(4) package(4) product_offering(4) role(4) system_config(2) user(4)
```

**JWT 无 `role` claim**，说明企业版完全依赖 Casbin 实时鉴权，社区版的 `role` 字符串判断是简化实现。

### 4.5 社区版内部的「企业版残留」

源码中已存在企业版痕迹，说明当前代码是从企业版裁剪而来，补齐成本低于全新开发：

| 残留 | 位置 | 说明 |
| --- | --- | --- |
| `tenant_id` 兼容分支 | `internal/database/migration.go:93-106` | 代码注释「兼容历史测试库保留的 tenant_id 必填列；社区版新库不会新增该列」 |
| Redis 缓存模块设计 | `docs/modules_design/2025.12.30-增加redis缓存模块.md` | 文档已设计，代码未实现 |
| `company_size` / `customer_level` | `internal/models/customer.go` | 模型有字段，DB 列缺失 |
| 迁移序号 007 / 008 空缺 | `backend/migrations/` | 编号跳号，对应企业版表 |
| `CHANGELOG` 版本语义 | 提交历史含企业版移除记录 | `removeLegacyAuthorizationCodeTypeFields` |

`tenant_id` 尤其关键：它是多租户架构的痕迹，企业版很可能支持多租户 SaaS 模式，但当前演示环境未暴露该能力。

## 5. 补齐优先级建议

按依赖关系分四批，**不建议并行推进全部 12 个模块**。

### P0 — 授权体系地基（必须先做）

| 项 | 理由 |
| --- | --- |
| 产品项管理 | 缺少授权策略归口层，后续功能模板、试用策略、产品级密钥都无处安放 |
| 功能模板 | 功能授权从 `feature_config` JSON 硬编码升级为可复用模板 |

依赖关系：产品项 → 功能模板 → 授权码改造 → 许可证验签升级。

### P1 — 系统管理（安全底线）

| 项 | 理由 |
| --- | --- |
| 用户管理 | 现无管理界面，多人协作无法开展 |
| 角色与权限 | Casbin RBAC，56 条权限粒度，涉及全站鉴权改造 |
| 系统配置 | 站点名/Logo/登录方式硬编码在代码里 |
| 菜单管理 | 依赖角色权限，配套项 |

依赖关系：用户 → 角色权限 → 菜单管理。

### P2 — 运营合规

| 项 | 理由 |
| --- | --- |
| 审计日志 | 有合规要求时必需；社区版仅 `authorization_changes` 覆盖授权码变更 |
| 设备台账 | 硬件交付量大时才有价值，纯桌面软件可不做 |
| API Key | 第三方系统集成时需要 |
| 忘记密码 | 依赖邮件/短信服务配置 |

### P3 — 客户自助端（建议独立立项）

| 项 | 理由 |
| --- | --- |
| 注册登录 / 套餐 / 支付 / 自助取码 / 设备解绑 / 发票 / 订单 / 线索 | **这是独立业务线，不是管理端功能扩展** |

涉及支付、发票、短信、邮件全套外部依赖，且需要独立的用户体系与前台设计。建议单独排期，不与 P0–P2 混做。

## 6. 决策记录（2026-10-09 已定）

| # | 决策点 | 结论 |
| --- | --- | --- |
| 1 | 是否走 Casbin | **引入**。56 条权限粒度照实落地 |
| 2 | 登录响应变更 | **版本化**：新增 `/api/v2/login`，v1 保持不变 |
| 3 | 客户自助端是否纳入 | **本期不做**。连带发票/套餐/企业线索一并移出（一并依赖自助端数据来源） |
| 4 | 产品项 code 策略 | **系统自动生成、不可更改**；用户另填 `alias` 用于界面显示（与实测企业版 UI 有偏离） |
| 5 | 是否需要多租户 | **不引入**。新表不预留 `tenant_id`，遗留兼容分支保留 |
| 6 | i18n 响应消息 | **不做统一改造**。判定「全量接口按 `Accept-Language` 输出」为过度设计，取消该方案；现有三语错误体系保留不动 |
| 7 | 圆角策略 | **统一 4px**，对齐企业版 |
| 8 | Casbin 适配器 | **自定义 DB adapter 直接查 `roles` 表**，不用 file adapter，避免策略文件与 DB 双写 |

**仍待确认**：

- 商业授权边界：本项目 GPL-3.0，企业版功能需确认授权条款与开源合规
- 客户自助端延后是否影响本期商业化目标（无法自助购买/开票）
