# 1panel「运行环境」部署指南（Go + 静态站点）

> 适用：已在 1panel 面板中，用「网站 → 运行环境（Go）」托管后端、「静态网站」托管前端。  
> 不使用 systemd，不使用 Docker 编排，进程由 1panel 运行环境管理。  
> 核心交付：**后端启动命令**（见 §3），以及配套的前端与反代配置。

---

## 0. 方案结构

```
1panel 面板
├─ 运行环境（Go）  license-backend   ← 后端 Go 程序，监听容器内 :18888
│    启动命令: sh deploy/1panel/start-backend.sh
│    环境变量: DATABASE_PASSWORD / AUTH_JWT_SECRET
│
└─ 静态网站        license-ui        ← 前端 dist/ 产物 + 反向代理 /api → 后端
     （或用「反向代理」类型指向后端端口）
```

**为什么需要启动脚本而不是直接写命令**：后端配置里的 `i18n.config_path` 与  
`license.rsa.*_key_path` 是**相对当前工作目录**解析的，不是相对配置文件位置。

| 启动 cwd         | 配置前缀             | 解析结果                    |
| -------------- | ---------------- | ----------------------- |
| `backend/`     | `configs/...`    | `backend/configs/...` ✅ |
| `backend/cmd/` | `../configs/...` | `backend/configs/...` ✅ |

容器里 1panel 设定的工作目录未必是 `backend/`，直接写 `./license-manager -config configs/config.local.yaml`  
有极大概率因找不到 i18n/RSA 文件而 `log.Fatalf` 启动失败。`start-backend.sh` 自动定位项目根并切到 `backend/`，消除这个不确定性。

## 0.5 1panel Go 运行环境的真实机制

以下来自 1panel 官方 appstore 模板 `apps/go/<版本>/docker-compose.yml` 与 `run.sh`，**理解这几条能解释绝大多数「看起来奇怪」的现象**。

```yaml
services:
  golang:
    image: golang:${GO_VERSION}
    working_dir: /app                                  # ← 容器工作目录
    volumes:
      - ${CODE_DIR}:/app        # ← 你填的「运行目录」挂载到 /app（持久）
      - ./run.sh:/run.sh
      - ./.env:/.env            # ← 运行环境目录下生成的 .env
      - ./mod:/go/pkg/mod       # ← ★ mod 缓存挂载（持久，官方已挂好）
    command: bash /run.sh
    restart: on-failure:5      # ← 失败最多重启 5 次后停止
```

```bash
# run.sh
source /.env
eval $EXEC_SCRIPT              # ← 你填的「启动命令」存为 EXEC_SCRIPT，在此 eval 执行
```

关键结论：

| 项 | 实际值 |
| --- | --- |
| 源码位置 | 容器内 `/app`（= 你填的运行目录，**已持久化挂载**） |
| 容器工作目录 | `/app`（**不是** `backend/`） |
| 你填的启动命令 | 写入 `.env` 的 `EXEC_SCRIPT`，由 `run.sh` 用 `eval` 执行 |
| mod 依赖缓存 | 容器内 `/go/pkg/mod` → 运行环境目录的 `mod/`，**官方已持久化挂载** |
| 运行时目录 | `/opt/1panel/runtime/go/<你填的名称>/`（含 `.env`、`mod/`、`run.sh`） |
| 失败重启 | `on-failure:5`——启动失败会反复重启 5 次后停止 |

**由此推出的三个要点**：

1. **mod 缓存不需要你自己重定向**。官方已把 `/go/pkg/mod` 挂载到持久目录，
   依赖下载后天然跨容器重建保留。若再把 `GOMODCACHE` 改到项目目录，
   反而会绕开官方那个持久位置，造成两份 mod 缓存（双倍磁盘）。
2. **启动命令用相对路径即可**，因为 cwd 恒为 `/app`（= 项目根）：
   `sh deploy/1panel/start-backend.sh` 可正常解析。
3. **「日志不刷新」通常意味着进程根本没在跑**。官方 restart 策略是 `on-failure:5`，
   启动脚本一旦报错，容器会反复重启直至停止，面板日志里只会反复出现同一段启动错误。
   面板的「查看日志」用的是 `docker logs -f`（follow 模式，默认开启），
   本身不会卡住——问题在应用侧。

## 1. 前置准备

### 1.1 服务器上放好代码

```bash
# 建议放在 1panel 便于管理的位置
mkdir -p /opt/1panel/runtime/license-manager
cd /opt/1panel/runtime/license-manager
git clone <你的仓库地址> .
git checkout main
```

### 1.2 准备配置与密钥

```bash
cd /opt/1panel/runtime/license-manager

# 一键完成：.env + JWT_SECRET + RSA 密钥替换 + 密钥 git 保护
bash scripts/deploy-prepare.sh

# 后端配置（从模板复制，路径前缀 configs/ 适配从 backend/ 启动）
cp backend/configs/config.local.yaml.example backend/configs/config.local.yaml
vi backend/configs/config.local.yaml
```

`config.local.yaml` 必改项：

```yaml
server:
  mode: "release"           # ⚠️ 必须改！见下方「JWT 密钥兜底规则」

database:
  host: "127.0.0.1"        # MySQL 在宿主机则填 127.0.0.1；容器内需用宿主机内网 IP
  port: 3306
  username: "license_user"
  password: "你的强口令"     # 也可留空，用环境变量 DATABASE_PASSWORD 覆盖
  database: "license_manager"

auth:
  jwt:
    secret: "please-change-in-prod"   # 占位符；建议由环境变量 AUTH_JWT_SECRET 注入
```

### JWT 密钥兜底规则（后端自动执行）

后端启动时若检测到 JWT 密钥是弱值，会**自动生成随机强密钥**并打 `[WARN]`：

| 密钥值 | `server.mode` | 行为 |
| --- | --- | --- |
| 空值 | 任意 | 替换为随机强密钥 + `[WARN]` |
| `please-change-in-prod`（占位符） | 任意 | 替换为随机强密钥 + `[WARN]` |
| `license-manager-default-secret-key`（viper 默认值） | 任意 | 替换为随机强密钥 + `[WARN]` |
| `license-manager-dev-secret-key-32-bytes`（开发固定密钥，随仓库公开） | **release** | 替换为随机强密钥 + `[WARN]` |
| `license-manager-dev-secret-key-32-bytes` | debug | **保留**（本地调试令牌稳定） |

⚠️ **自动生成的随机密钥仅存于内存，重启即失效、所有已签发令牌作废**——只是兜底，不是常态。
生产环境务必用环境变量 `AUTH_JWT_SECRET` 注入**固定**的强随机值（`openssl rand -hex 32`）。

> 这条规则也说明为什么 `server.mode` 必须改成 `release`：
> 开发固定密钥在 release 模式下会被强制替换，但仅内存态；只有环境变量注入才是稳定的。

> ⚠️ 若 MySQL 跑在**另一个容器**里，`host` 不能填 `127.0.0.1`（那是容器自身）。  
> 填宿主机的内网 IP（如 `172.17.0.1` 或实际网卡 IP），并确保 MySQL 监听非 127.0.0.1。

### 1.3 预编译后端二进制（推荐，避免容器内编译）

```bash
cd /opt/1panel/runtime/license-manager/backend
go build -o ../bin/license-manager cmd/main.go
ls -lh ../bin/license-manager
```

容器内若无 Go 工具链，**必须**在宿主机预编译（脚本会自动检测并给出提示）。

### 1.4 Go 依赖缓存（容器内编译时）

**官方已处理好 mod 缓存**，无需额外配置。1panel 的 Go 运行环境 compose 里有：

```yaml
- ./mod:/go/pkg/mod      # 运行环境目录下的 mod/，随运行环境持久化
```

即容器内 `/go/pkg/mod` 映射到 `/opt/1panel/runtime/go/<名称>/mod/`，**容器重建后依赖仍在**，
不会每次重启都重新下载。首次编译耗时较长（约 1–3 分钟，取决于网络），之后走缓存。

只有**编译缓存**（`GOCACHE`，默认在容器可写层 `/root/.cache/go-build`）会随容器重建丢失，
`deploy/1panel/start-backend.sh` 已把它指向项目内 `.cache/build`（项目目录是挂载目录，同样持久）。

若你手动编译（不用启动脚本），可自行指定：

```bash
cd /opt/1panel/runtime/license-manager
mkdir -p .cache/build
export GOCACHE=$PWD/.cache/build
export GOPROXY=https://goproxy.cn,direct     # 国内加速
cd backend && go build -o ../bin/license-manager cmd/main.go
```

> ⚠️ **不要改 `GOMODCACHE`**：官方已把 `/go/pkg/mod` 挂载为持久目录，
> 改到项目目录会绕开它，造成两份 mod 缓存（磁盘占用翻倍）且官方那份形同虚设。
>
> ⚠️ `.cache/` 已加入 `.gitignore`（编译缓存体积可观，**严禁提交**）。
> 宿主机预编译则不需要这套机制——不产生缓存，也没有重下依赖的问题。

## 2. 创建后端运行环境（1panel）

面板路径：**网站 → 运行环境 → 创建运行环境 → Go**

| 表单字段     | 填写值                                   | 说明                          |
| -------- | ------------------------------------- | --------------------------- |
| **运行目录** | `/opt/1panel/runtime/license-manager` | 项目根（含 `backend/`、`deploy/`） |
| **启动命令** | `sh deploy/1panel/start-backend.sh`   | 见 §3                        |
| **端口**   | `18888`                               | 后端监听端口                      |
| **环境变量** | 见下                                    | 注入敏感配置                      |

环境变量（逐条添加）：

```
DATABASE_PASSWORD=你的数据库强口令
AUTH_JWT_SECRET=你的JWT随机密钥
TZ=Asia/Shanghai
GIN_MODE=release
```

> `AUTH_JWT_SECRET` 用 `openssl rand -hex 32` 生成。留空的话后端会退回自动生成随机密钥，  
> **重启即失效、所有已签发令牌作废**，仅作兜底。

创建后点「启动」，用「查看日志」确认输出：

```

[start] 使用已有可执行文件: /opt/1panel/runtime/license-manager/bin/license-manager
[start] 工作目录: /opt/1panel/runtime/license-manager/backend
[start] 配置文件: configs/config.local.yaml
[start] 监听地址: 0.0.0.0:18888
```

验证（宿主机执行，端口按 1panel 实际映射填写）：

```bash
curl -fsS http://127.0.0.1:18888/health
```

## 3. 启动命令（三选一）

### 方案 A（推荐）：用仓库内置脚本

启动命令填：

```
sh deploy/1panel/start-backend.sh
```

脚本自动完成：定位项目根 → 检查环境变量 → 检查配置文件 → 准备二进制 → `cd backend/` → `exec` 启动。

### 方案 B：宿主机预编译 + 手写命令

若不使用脚本，启动命令填（**注意 cwd**）：

```
cd backend && exec ../bin/license-manager -config configs/config.local.yaml
```

### 方案 C：容器内现场编译

启动命令填：

```
sh deploy/1panel/start-backend.sh
```

并**不要**预编译——脚本检测到无 `bin/license-manager` 且容器内有 `go` 时会自动编译。  
容器内无 Go 工具链时此方案不可用（脚本会明确报错）。

### ⚠️ 不要这样写

```
./license-manager -config configs/config.local.yaml
```

cwd 不确定 → 相对路径解析到错误位置 → 启动即失败。

### 启动命令的三个硬性要求

1. **必须 `exec`**：让后端成为容器主进程（PID 1），否则 1panel 停止/重启时信号传不到，进程可能残留。
2. **必须指定 `-config`**：否则程序按 `config.yaml` → `../configs/config.yaml` 顺序查找，容器里通常都不存在。
3. **cwd 必须是 `backend/`**：保证 `configs/...` 相对路径指向正确。

## 4. 前端部署（1panel 静态网站）

### 4.1 构建前端

在**有 Node 20 + pnpm 的机器**（可与后端同机）执行：

```bash
cd /opt/1panel/runtime/license-manager/frontend
pnpm install
VITE_OUTDIR=dist VITE_ADDRESS_BASE_URL=/ pnpm run build:prod
ls -la dist/     # 应有 index.html / static/ / favicon.svg
```



> ⚠️ 必须传 `VITE_OUTDIR=dist VITE_ADDRESS_BASE_URL=/`。  
> 仓库 `frontend/.env.production` 中是 `VITE_OUTDIR='production'` 与 `VITE_ADDRESS_BASE_URL='/production/'`，  
> 不覆盖会产出到 `frontend/production/` 且资源路径带 `/production/` 前缀，导致页面白屏。

### 4.2 放置产物

把 `dist/` 传到 1panel 静态站点的运行目录，例如 `/opt/1panel/www/sites/license-ui/index`：

```bash
sudo mkdir -p /opt/1panel/www/sites/license-ui/index
sudo rsync -a --delete frontend/dist/ /opt/1panel/www/sites/license-ui/index/
```

### 4.3 创建静态网站

面板路径：**网站 → 创建网站 → 静态网站**

| 字段           | 填写值                                      |
| ------------ | ---------------------------------------- |
| **代号**       | `license-ui`                             |
| **主域名**      | `license.example.com`（可加端口）              |
| **网站目录**     | `/opt/1panel/www/sites/license-ui/index` |
| **启用 HTTPS** | 开启并申请证书                                  |

### 4.4 配置 `/api` 反向代理（关键）

静态站点默认不会把 `/api` 转给后端，**必须配反代**，否则前端所有接口 404。

两种做法：

**做法一：编辑 1panel 生成的站点 OpenResty 配置**  
在站点的「配置」中，于 `server` 块内加入：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:18888;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_connect_timeout 60s;
    proxy_read_timeout 60s;
}

# Vue Router history 模式
location / {
    try_files $uri $uri/ /index.html;
}
```

**做法二：改用「反向代理」网站类型**  
网站 → 创建网站 → 反向代理 → 代理地址填 `http://127.0.0.1:18888`。  
但注意：后端只提供 API，不提供前端静态资源，**这种方式前端页面无法访问**。  
因此本项目**只能用做法一**（静态网站 + 站点内配 `/api` 反代）。

> 为什么反代到 `127.0.0.1:18888`：后端运行环境的端口已由 1panel 映射到宿主机。  
> 若 1panel 映射的是其他端口（如 `28888`），请同步修改 `proxy_pass`。  
> 前端用相对路径 `/api/...` 请求（生产 `VITE_API_BASE_URL` 为空），反代后浏览器始终同源，**完全绕开 CORS**。

## 6. 常见问题

### 6.0 先做这一步：看容器真实状态

面板日志不刷新、缓存目录没内容时，**先在服务器终端确认容器到底在不在跑**：

```bash
# 找到运行环境对应的容器名
docker ps -a --filter "name=<你填的环境名称>" --format "table {{.Names}}\t{{.Status}}"

# 看容器日志（这是面板「查看日志」的数据源）
docker logs --tail 100 <容器名>

# 进容器手动跑一次启动命令，看真实报错
docker exec -it <容器名> bash -c 'cd /app && sh deploy/1panel/start-backend.sh'
```

容器 `Status` 若是 `Restarting` 或 `Exited (1)`，说明启动脚本在报错。
**容器内手动执行启动命令是最快的定位手段**——它会打印完整诊断信息
（项目根、挂载状态、缓存目录、编译产物），可直接看出卡在哪一步。

> 面板的「查看日志」用的是 `docker logs -f`（follow 模式，默认开启），
> 本身不会卡住。所以「日志不刷新」几乎总是**应用侧没在输出**——进程已退出或正在反复重启。

### 6.1 对照表

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 容器状态 `Restarting` / `Exited` | 启动脚本报错 | `docker logs <容器名>` 看报错；常见是缺 `config.local.yaml` |
| 面板日志不刷新 | 进程没在跑（容器已停止） | 同上，先看容器状态 |
| 面板日志反复刷同一段错误 | `restart: on-failure:5` 反复重启 | 修掉报错即可；脚本会打印 `[start] ...` 定位到具体阶段 |
| 「缓存目录下没有下载的 mod」 | mod 缓存在**官方挂载点** `/go/pkg/mod`，不在项目目录 | 正常现象。确认：`docker exec <容器名> du -sh /go/pkg/mod` |
| 想确认是否每次重下依赖 | 官方已挂载持久目录 | 不会重下；`/go/pkg/mod` → 运行环境目录的 `mod/` |
| `unbound variable` 报错 | shell 变量后紧跟中文全角标点（如 `$CACHE_DIR（`） | 已在新版脚本修复；自行修改脚本时变量与全角标点间加空格或用 `${VAR}` |
| 容器内编译报网络错误 | 直连 `proxy.golang.org` 不通 | 脚本已默认 `GOPROXY=https://goproxy.cn,direct`；也可在环境变量中设置 |
| 后端反复重试连 MySQL | MySQL 不可达 | 容器内 `127.0.0.1` 指向容器自身，MySQL 在宿主机时须填宿主机内网 IP |
| 报 `failed to read config file` | 启动命令未带 `-config` | 用 §3 方案 A/B |
| 报 `i18n ... no such file` / `RSA ... no such file` | cwd 不对，相对路径解析错位 | 必须用启动脚本，或 `cd backend && ...` |
| 前端白屏 | 资源路径带 `/production/` 前缀 | 重新构建时传 `VITE_OUTDIR=dist VITE_ADDRESS_BASE_URL=/` |
| 前端接口全 404 | 站点未配 `/api` 反代 | 见 §4.4 |
| 登录后刷新 404 | 缺 history 模式 fallback | 站点配置加 `try_files $uri $uri/ /index.html` |
| 停止运行环境后端口仍占用 | 启动命令未用 `exec` | 用 §3 方案 A/B |
| 令牌每次重启都失效 | `AUTH_JWT_SECRET` 未设，用了自动生成的内存密钥 | 在运行环境环境变量中固定该值 |

### 6.2 启动脚本的诊断输出

`deploy/1panel/start-backend.sh` 启动时会打印一段诊断信息，用于快速确认容器内环境：

```
[start] 项目根: /app
[start] ---- 运行环境诊断 ----
[start] 容器内工作目录(启动时): /app
[start] 源码是否挂载: 是 (/app 为 CODE_DIR 挂载点)
[start] 官方 mod 缓存挂载点: /go/pkg/mod (272M)
```
